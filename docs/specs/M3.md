# M3: Party and progression data model plus save/load schema (S7 + S13, merged)

Status: proposed
Depends on: nothing unmerged for the logic (reads `StatRules`, `ContentCatalog`, `ContentFactory`, `Combatant` as they are). Soft: M2C2B only changes which skills a path grants; this milestone derives them, so it can run in parallel with M2C2B and AI1.
Lane: logic only (the XP curve JSON is part of the logic task; no asset task)
Touches: new `scripts/progression/*`, new `scripts/game_state/*`, new `data/progression/xp_curve.json`, new `scripts/tests/progression_test_suite.gd` and `scripts/tests/save_test_suite.gd`; ADDITIVE only in `scripts/core/inventory/*` (serialisation helpers, if missing) and `scripts/content/content_factory.gd` (at most one new build function or optional parameters); one registration block in `arena_test_suite.gd`; README, `docs/STRUCTURE.md` (placeholders become `done`). `combatant.gd`, `content_schema.gd`, `content_catalog.gd`, `skill_def.gd` are NOT edited.

## Goal

Define the persistent party snapshot once and use it for both progression and saving: a `UnitState` per party member (level via XP, confirmed stat spend, learned skills, passives, loadout, gear), a `PartyState`, a session-wide `GameState` (world, location, party, flags, an opaque quests blob owned later by S8), the XP curve and level-up rules as pure functions, a builder that turns a state into a `Combatant` identical to a catalog-built one, and a versioned single-slot JSON save with a migration hook and a new-game constructor. No UI. Merging S7 and S13 is deliberate: the save schema IS the state model, and building them apart would force a schema retrofit.

## Schema contract (logic lane)

Schema-first: not needed (no asset lane). Everything is plain data with `to_dict()` / `static from_dict()` and a `validate(catalog) -> Array[String]` per class (empty = valid). JSON numbers come back as floats: convert with `DictUtil.to_int` on load.

### UnitState (`scripts/progression/unit_state.gd`)

| Field | Type | Default | Allowed / validation |
| --- | --- | --- | --- |
| id | String | required | id charset `[a-z0-9_]`, unique inside the party |
| base_unit | String | required | must be a `ContentCatalog` unit id (party side) |
| lore_ref | String | "" | empty or a qualified world character id; not validated against a world here |
| total_xp | int | 0 | >= 0; level is DERIVED from it (no stored level) |
| spend | Dictionary | {} | stat (`StatRules.STATS`) -> int >= 0; confirmed points only; sum <= `StatRules.spend_pool(level)`; per-stat ceiling as `StatRules.validate_spend` enforces; missing stats = 0 |
| learned_skills | Array[String] | [] | skill ids that exist in the catalog; extras beyond the class path (maps to `Combatant.granted_skills`) |
| passives | Array[String] | [] | passive ids that exist in the catalog; permanent (DECISIONS: passives permanent) |
| loadout | Dictionary | {"class": [], "extra": []} | family ids; <= `MAX_CLASS_SLOTS` / `MAX_EXTRA_SLOTS`; every family must be owned (class path at level or learned); empty = default loadout |
| equipment | Dictionary | {} | slot name (as `Equipment` uses) -> item id; item must exist; class proficiency must allow it (re-use the Inventory/Equipment rules) |
| carried | Array[String] | [] | item ids in the unit's own carry |

Derived (never stored): `level` (from the curve), `unspent` = `spend_pool(level)` minus sum(spend), `class_id` (from the base unit), `skill_cap` (`StatRules.skill_cap_for_level`).

Temporary passives granted by scripted fights are runtime only and are never written (explicit test).

### PartyState (`party_state.gd`)

| Field | Type | Default | Allowed / validation |
| --- | --- | --- | --- |
| members | Array[UnitState] | [] | 1..`PARTY_MAX` (const, starting value 4, see open question 1); unique ids |
| active_ids | Array[String] | [] | subset of member ids, size <= `PARTY_MAX`; empty = all members |
| stash | Dictionary | {} | item id -> count (int >= 1); item must exist |

### GameState (`scripts/game_state/game_state.gd`)

| Field | Type | Default | Allowed / validation |
| --- | --- | --- | --- |
| world_id | String | required | non-empty id (WorldCatalog existence checked by `NewGame`, not by the data class) |
| location_id | String | "" | optional id |
| party | PartyState | required | valid |
| flags | Dictionary | {} | String key `[a-z0-9_.]` -> bool, int or String (the S8 flag registry reads and writes it) |
| quests | Dictionary | {} | opaque to this milestone: saved and loaded verbatim (S8 defines it); must be JSON-safe |

### XP curve (`data/progression/xp_curve.json`, `scripts/progression/xp_curve.gd`)

```json
{"version": 1, "xp_to_next": [40, 70, 110, 160, 220, 290, 370, 460, 560],
 "kill_xp": {"base": 10, "per_level": 5,
             "tier_mult": {"minion": 0.5, "standard": 1.0, "elite": 2.0, "boss": 5.0, "hero": 1.0},
             "level_delta_step": 0.15, "level_delta_min": 0.25, "level_delta_max": 2.0}}
```

Validation: `xp_to_next` has exactly `StatRules.MAX_LEVEL - 1` positive ints; tiers equal `StatRules.tier_names()`; all multipliers > 0; `level_delta_min` <= 1 <= `level_delta_max`. These numbers are starting values for BAL1 (cumulative XP to reach level 2..10: 40, 110, 220, 380, 600, 890, 1260, 1720, 2280). The loader returns defaults and an error list if the file is invalid (never crashes).

### SaveGame (`save_game.gd`) and migrations (`save_migrations.gd`)

- Envelope: `{"format": "fc_save", "version": 1, "saved_at": <unix int>, "game_state": {...}}`. Constant `SaveGame.VERSION = 1`.
- Path: `user://saves/slot_<n>.json`; API takes the slot int (only slot 1 used now); the base directory is a static override so tests and the Dojo/Forge sandboxes never touch real saves.
- `SaveGame.write(state, slot) -> Array[String]` (errors; validates first and refuses an invalid state; writes `<file>.tmp` then renames, so a crash never leaves a half file).
- `SaveGame.read(slot) -> Dictionary` = `{"ok": bool, "errors": Array[String], "state": GameState or null}`. Never returns a partially loaded state.
- `SaveMigrations.migrate(data: Dictionary) -> Dictionary` applies `from_version -> from_version+1` steps in order from a table (empty at version 1); a save with a HIGHER version than `VERSION` is refused with the message "save is from a newer version"; unknown extra keys inside `game_state` are dropped and listed as warnings.
- `SaveGame.exists(slot)`, `SaveGame.delete(slot)`.

## Rules (logic lane)

1. Level from XP: `level` = 1 + number of cumulative thresholds reached, capped at `StatRules.MAX_LEVEL`; at max level `total_xp` may keep growing but the level is 10. `XpCurve.xp_for_level(L)` is the inverse; `UnitState.at_level(base_unit, level)` sets `total_xp` to exactly the threshold of that level (used by tests, sims and new games).
2. Awarding XP: `LevelUp.award(state, xp) -> {levels_gained, old_level, new_level, unspent}` adds XP, returns the derived changes. The spend pool grows by `FREE_PER_LEVEL` per level (the pool formula is `StatRules.spend_pool`); confirmed points are permanent (no respec in this milestone).
3. Kill XP: `XpCurve.kill_xp(enemy_level, enemy_tier, member_level) = round((base + per_level x enemy_level) x tier_mult x clamp(1 + level_delta_step x (enemy_level - member_level), level_delta_min, level_delta_max))`, min 1. Encounter XP = sum over defeated enemies; every party member in the active party gets the full amount (including a downed member); non-active members get none.
4. Spend: `LevelUp.confirm(state, draft) -> Array[String]` adds `draft` (stat -> int) to `spend` if the sum of the draft <= `unspent` and the result passes `StatRules.validate_spend` partial rules; errors leave the state untouched (undo = discard the draft before confirm). `LevelUp.auto(state, class_growth)` spends all `unspent` by `StatRules.auto_spend` (automatic path for sims and presets). Building a `Combatant` requires `unspent == 0`: the builder calls `auto` on a copy if points remain (documented, state unchanged).
5. Skills: the class path grants skills by level exactly as today; `learned_skills` are added through `Combatant.learn_skill`; the default loadout rule is unchanged; a non-empty stored `loadout` is applied with `set_loadout` and an invalid one falls back to the default with a warning string.
6. `PartyBuilder.build(unit_state, catalog) -> Combatant`: uses the existing catalog/factory path for class, tier and gear, level from XP, spend from the state, then applies passives, learned skills, loadout, equipment. Equivalence: for a state made with `at_level(base_unit, L)` and the base unit's authored spend, the built `Combatant` has the same `max_hp`, `speed`, stats, known skills, active families and equipment as the catalog-built unit of level L (no numbers change).
7. `NewGame.create(world_id, base_unit_ids: Array[String]) -> GameState`: members at the base unit's authored level, `total_xp` = threshold of that level, empty spend (= auto), default gear; refuses unknown units or a world id not found by `WorldCatalog`; returns the state and an error list.
8. Round trip: `GameState.to_dict()` -> JSON string -> parse -> `from_dict()` yields an equal state (deep equality helper `equals`), with ints preserved.
9. Flags: `GameState.set_flag/get_flag/has_flag/clear_flag` with key validation; no other behaviour (S8 builds on it).

### Acceptance checks (rule-derived)

- XP: `level_for(xp_for_level(L)) == L` for L 1..10; `level_for(xp_for_level(L) - 1) == L - 1` for L 2..10; level never exceeds 10; thresholds match the cumulative sums of the file (derive from the JSON, not literals).
- Kill XP: a tier ladder at equal level is minion < standard < elite < boss with the file multipliers; delta clamps at the min and max; result >= 1.
- Spend: a draft above `unspent` is refused with an error and no state change; a valid draft reduces `unspent` by its sum; after `auto` unspent is 0 and `StatRules.validate_spend(spend, level)` is empty for every class at levels 1..10; level up raises `unspent` by exactly 1 (derive from `FREE_PER_LEVEL`).
- Equivalence (rule 6) for each of the six classes' catalog party units at levels 1, 5, 10, with gear.
- Passives and skills: a state with a granted passive and a learned skill builds a combatant that has them; temporary passives never appear in `to_dict()`.
- Validation: unknown base unit, duplicate member id, spend sum above the pool, loadout with an unowned family, missing item, bad flag key: each yields an error string and `SaveGame.write` refuses.
- Save: write then read gives an equal state; reading a corrupt/truncated file returns `ok == false` with an error and no state; version 2 file returns the "newer version" error; a registered test-only migration 1 -> 2 transforms a fixture (proves the hook); the temp file never remains after a successful write; writes go only to the sandbox directory (assert the real `user://saves` is untouched by the suite).
- New game: valid input creates a valid state; unknown unit or world refuses.
- Determinism and isolation: no global rng, no scene dependencies (`RefCounted` only), strict typing, no UNSAFE_ calls.

## Out of scope

- Level-up UI, party screen, main menu, new-game screen, multiple slots and autosave (growth path B), respec, persistent HP/wounds between fights, gold/shops (S11), the quest runtime and flag registry rules (S8), travel, balance tuning of the curve (BAL1), cloud/sandbox saves for Dojo/Forge beyond the directory override.

## Open questions

1. Party size: is `PARTY_MAX` 4 right (starting value), and may the player carry more members than are active in a fight?
2. HP between fights: full heal after every battle (default here) or persistent damage with rest/heal costs? (Persistent HP would add a field and an economy.)
3. Respec: permanent spend (default) or a cheap respec at a trainer (S11)?
4. XP split: every active member gets the full encounter XP (default). Alternative: split among members, or only members who acted.

## Answers (user, 2026-10-16)

1. `PARTY_MAX` 4 active; the roster may be larger than the active party.
2. Full heal after every battle (persistent damage is a later option).
3. Spend is permanent (no respec for now).
4. Every active member gets the full encounter XP.
