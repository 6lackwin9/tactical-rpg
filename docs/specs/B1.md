# B1: Rest enters Tactical stance; stance-switch cost framework

Status: approved
Depends on: slice A (done)
Lane: logic

## Goal

Rest is a tactical action (it gains AP), so it should leave the unit in Tactical stance, not Neutral. Make stance-switch costs data-friendly so they can be retuned without code changes. Today: `SkillDef.stance()` returns NEUTRAL for REST, `switch_cost()` is 0 for REST and for stance-keeping kinds, otherwise 1 when the stance differs.

## Schema contract

- No new skill fields required. Optional (only if cheap): a skill-level override `switch_cost_override` (int, -1 = rule default) so a single skill can be made free or dearer later; validation 0..2.
- Named constants in one place (`StatRules` or `CombatTypes`): `STANCE_SWITCH_COST = 1`.

## Rules

1. REST puts the unit in TACTICAL (`SkillDef.stance()` for Kind.REST returns TACTICAL). Entering that stance via Rest stays free (Rest never pays a switch).
2. The skill after Rest pays the usual switch only if its stance differs from Tactical: Focus (Tactical) is free after Rest, an Offensive attack costs +1, a Defensive skill costs +1. So Rest then attack nets +1 AP (2 recovered, 1 switch), Rest then Focus nets +2.
3. The matchup consequence is accepted: a resting unit is Tactical, which loses to Offensive and beats Defensive (existing matrix); no matrix change.
4. All hard-coded `1` switch costs use `STANCE_SWITCH_COST`; `switch_cost_override` (if added) wins when >= 0.
5. Move, Switch Target, statuses, Disengage and SUPPORT (without stance_override) keep the current stance exactly as today.

## Acceptance checks (rule-derived)

- A rested unit's stance is Tactical after the Rest resolves; planner `stance_after` for Rest is Tactical.
- Rest then Focus: total AP spent = skill AP only (no switch); Rest then an Offensive attack: attack AP + STANCE_SWITCH_COST.
- Recovered AP and AP-debt behaviour of Rest unchanged.
- Existing tests that assumed Rest returns to Neutral are updated to Tactical with the expectation derived from `SkillDef.stance()`; Dojo Rest checks (Dojo-37/38) updated the same way.
- The constant is used everywhere a switch cost is computed (grep for literal switch +1 logic in planner, resolver, dojo and AI estimates).

## Out of scope

- Reworking the stance matrix, changing Guard/Focus/attack stance definitions, new skills, balance.

## Open questions

- None; if the Dojo or AI treat Neutral specially after Rest, report it.
