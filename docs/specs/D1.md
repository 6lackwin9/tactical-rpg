# D1: weaken status, intimidate family, riposte tier change

Status: proposed
Depends on: slice A (done; `StatusRegistry`, `skill_potency` hook)
Lane: both. Logic part D1-L (schema first), asset part D1-A (needs D1-L).

## Goal

Add `weaken` (the afflicted unit deals less with its skills) to the `StatusRegistry`, add the `intimidate` family (three tiers, no damage, applies weaken) as the Warrior's fourth class family replacing hamstring, and change riposte to option A (AP 1/2/3, mitigation 0.15/0.20/0.25, counter stays 50%) with every riposte number coming from skill data so the reverse model (AP 2/1/0, mitigation 0.15/0.05/0) is a data-only change. `DamageCalculator.compute` is not touched (decision: combat extensions stay isolated from the formula).

## Schema contract (logic lane, D1-L, schema-first: yes)

### Registry row

Add `const WEAKEN: String = "weaken"` to `StatusEffects` and this row to `StatusRegistry.ROWS` (follow the header checklist; the registry test requires the row):

| id | kind | resistable | default_rounds | stacking | cap | display | grant |
| --- | --- | --- | --- | --- | --- | --- | --- |
| weaken | debuff | true | 2 | refresh_max_duration | 25 | Weakened | "" |

Meaning of the existing rule for this row: a second application keeps the longer rounds and the STRONGER magnitude, never the sum (non-stacking), and the magnitude (the instance's potency channel, in percent) is capped at 25 by the registry `cap`. Resist key: `weaken` (unit `status_resist["weaken"]`, passive `resist` effect, `debuff_resistance`; 100 = immune); it joins `StatusEffects.resistable()` automatically.

### Skill field `status_magnitude`

| Field | Type | Default | Allowed | Validation |
| --- | --- | --- | --- | --- |
| status_magnitude | int | 0 | 0..95 | required 1..25 when `status_effect` is `weaken` (error "weaken needs a magnitude 1-25"); must be 0 for every other status (error "magnitude only applies to weaken") |

`status_potency` keeps its meaning (hit chance, reduced by resistance). The magnitude is NOT rolled; it is what the applied instance carries. `StatusEffects.try_inflict(target, status, potency, rng, rounds)` gains an optional `magnitude` parameter (default 0, ignored by non-weaken statuses). The stored instance for weaken holds the magnitude in the same potency slot that `StatusRegistry.stack` combines, so the registry cap (25) and the refresh/max rule apply with no new code in `stack`. If an instance record cannot carry both the roll potency and a magnitude for weaken, report it as a schema gap (do not guess).

### `power_mult` zero for debuff-only attacks (SCHEMA GAP, needed by intimidate)

Today `power_mult` has `min 0.05` and an ATTACK always deals damage. Change: `power_mult` min 0.0; a value of exactly 0.0 is valid only when `status_effect` is not empty (error otherwise: "A skill with no damage needs a status"). Rules for a zero-power ATTACK:

- The attack command applies no damage and calls no `DamageCalculator.compute`; the status roll still happens; the log shows the status line only.
- It is not a hit for reactions: `RiposteRules.counter` does not fire off it (no damage was dealt).
- The planner shows "No damage" and the status/magnitude in the option text; the AI estimate treats it as 0 damage.

### Weaken hook (outgoing power)

- Add `Combatant.weaken_factor() -> float` = 1 - magnitude/100 of the active weaken instance (1.0 when absent; magnitude clamped to the registry cap).
- `SkillDef.power_for(user)` = `power_mult x user.potency_for(family) x user.weaken_factor()`. Every attack path already reads `power_for` (plan entry attack and area commands, Dojo, planner estimate), so all outgoing ATTACK power follows.
- `RiposteRules.counter` multiplies its fixed 0.5 counter multiplier by the countering unit's `weaken_factor()` (a weakened unit counters weaker). The 0.5 constant stays.
- NOT affected: heals and cleanses (`SupportRules`), mitigation, `DamageCalculator.compute` (its file and tests stay untouched; a grep check in review).
- Timing: weaken follows the same queue rule as stagger/root (a status inflicted this round starts next round and lasts `status_rounds`); `power_for` must read the statuses active for the round being planned/resolved, the same state `blocked_blocks` reads.

### Cleanse and registry-derived lists

`cleanse_statuses: ["all"]` removes weaken (it is a debuff); named lists may include `weaken`. `StatusEffects.debuffs()/resistable()` and the schema `status_effect` options pick the new row up from the registry. The Forge status dropdown and the passive `resist` options list it.

## Rules (logic lane)

1. Applying weaken: roll `chance = status_potency - debuff resistance - weaken resistance` as for other statuses; on success the instance (rounds = `status_rounds`, magnitude = `status_magnitude`) is queued for next round.
2. Stacking: a target already weakened (active or pending) keeps `max` of the two magnitudes (capped 25) and the longer rounds; the sum never exceeds 25.
3. A weakened unit's every ATTACK `power_for` is multiplied by `1 - magnitude/100` for the instance's rounds; the multiplier is the same for single-target and area attacks and for the riposte counter.
4. Riposte (data driven): `RiposteRules` keeps only the counter constant (0.5). The skill's AP is its `level`, its mitigation is `mitigation`, its duration is `status_rounds`; no code path may contain riposte AP, mitigation or round constants. Tier rows may have any AP ordering, including descending (the reverse model); a validator rule that requires AP to rise with tier must be a warning, not an error, for the riposte family.
5. Zero-power attacks never count as a damaging hit anywhere (counters, "hit" logs, crits).

### Acceptance checks (rule-derived)

- Registry: `row_errors()` is empty; weaken row fields equal the table; the registry test passes with the new constant; `resistable()` contains `weaken`.
- Cap and non-stacking: stacking 15 then 25 gives 25, 25 then 15 gives 25, two 25s give 25 (never 50); rounds are the longer of the two.
- Hook: for a unit with a given base `power_for` P, an active weaken of m percent gives P x (1 - m/100) in `power_for`, in the planner estimate, and in the resolved `AttackCommand` damage (derive expected damage from `DamageCalculator.compute` with the reduced skill multiplier); an unweakened unit is unchanged; `damage_calculator.gd` has no diff.
- Resistance: with `status_resist["weaken"] = 100` the application never succeeds; with 0 and potency 100 it always does (seeded rng).
- Zero power: a zero-power `intimidate` deals 0 damage, cannot trigger riposte, still inflicts weaken; `validate_entry` rejects `power_mult` 0 with no status and `weaken` with magnitude 0 or above 25.
- Cleanse: `purify` (`all`) removes an active and a pending weaken.
- Riposte data-only: a test builds the reverse model in memory (three riposte rows with levels 2/1/1 and mitigation 0.15/0.05/0.0; AP 0 needs `level` min 0, see open question) and asserts that planner AP cost, Guard mitigation and granted rounds follow the rows exactly, with no riposte code touched.
- `riposte_test_suite.gd` T1 AP expectation changes from 2 to 1: derive it from the catalog entry, not from a literal.

## Assets (asset lane, D1-A; needs D1-L)

### intimidate family (Warrior; new)

Common fields: `kind` ATTACK, `area` NONE, `power_mult` 0.0, `stance` DEFENSIVE (keeps riposte alive: no stance change from a Defensive warrior), `offhand` false, `dash_tiles` 0, `status_effect` weaken, `blocks` 1 (fixed across tiers), `weapon_types` [], `min_proficiency` 0, `basic` false, `learned_only` true, `family` intimidate.

| Id | Name | Tier | Level (AP) | Reach min-max | status_potency | status_magnitude | status_rounds |
| --- | --- | --- | --- | --- | --- | --- | --- |
| intimidate | Intimidate | 1 | 1 | 1-2 | 70 | 15 | 2 |
| intimidate_2 | Intimidate II | 2 | 2 | 1-2 | 75 | 20 | 2 |
| intimidate_3 | Intimidate III | 3 | 3 | 1-3 | 80 | 25 | 3 |

Description (each tier): "Roar at a foe: 70% to Weaken it (-15% outgoing power for 2 rounds)", numbers per tier. Tier rule check (authoring defaults): AP +1 per tier, chance +5 per tier, rounds at most 3, magnitude at most the 25 cap.

### riposte family (existing id edited, two ids added)

| Id | Tier | Level (AP) | mitigation | status_rounds | Change |
| --- | --- | --- | --- | --- | --- |

| riposte_2 | 2 | 2 | 0.20 | 3 | new |
| riposte_3 | 3 | 3 | 0.25 | 3 | new |

Reverse model (not authored, for reference): levels 2/1/0, mitigation 0.15/0.05/0.0, same rounds. Switching is a data edit of these three rows only.

### hamstring

Not removed: it stays for the brawler and rogue (M2C2B authors its tiers). The Warrior's class path change (hamstring was never in the shipped warrior path; intimidate takes the fourth slot) is owned by M2C2B.

## Out of scope

- Other new statuses, per-status magnitude for existing statuses, enemy AI use of intimidate (AI1), balance runs, riposte counter percent per tier (stays 50%), UI beyond what the registry already feeds.
- Changing `DamageCalculator`.
