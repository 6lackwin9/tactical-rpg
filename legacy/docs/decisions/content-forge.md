# Decisions: content catalog and Forge

Settled; do not re-litigate without asking the user. Scope: S5 catalog API, Content Forge rules, origin, ranked skill storage. Rows moved unchanged from `docs/DECISIONS.md` on 2026-10-17 (CLN-10), in their original order; append new rows at the end of the table. Index and global rules: `docs/DECISIONS.md`; superseded rows: `docs/decisions/archive.md`.

| Decision | Choice | Why |
| --- | --- | --- |
| upsert_many (2026-10-16) | `ContentCatalog.upsert_many(kind, entries)` validates a set of entries together and applies all or none (restoring the previous state on any problem); needed for family-wide flags like `advanced` that must match across ranks (a single-row upsert is refused); the Forge skill editor will use it for ranked entries (FORGE1) | SK2-A finding |
| FORGE1 skills answers (user 2026-10-16) | Storage S3 accepted (ranked entries on disk, flat rows in memory) with the Forge showing the SKILL FAMILY for editing and the ranks in their own section; the weapon-gate section opens to DEFEND and SUPPORT; basics are enforced to exactly one rank; rank names are DERIVED ("Mend II"), not authored; descriptions support dynamic values from the rank modifiers (token placeholders resolved per rank) or keep numbers out of the text; the skill family is the TEMPLATE and each rank is derived from it by that rank's modifiers (resolve against the base, no cascade); length caps 32 (name) and 240 (description) accepted; `evolves_from` question still open | User 2026-10-16 |
| FORGE1 class answers (user 2026-10-16) | The Forge supports creating more classes; for now it is LOCKED against editing key fields of existing (system) assets so existing logic cannot break; DELETE only for user-created assets; system-generated assets are protected from deletion; a user asset that a game test uses is converted to system type (delete locked) - an `origin` concept (system / user) across all Forge kinds; AI: the class keeps `ai_role` only (used as the unit's default role; other class AI editing dropped/disabled in the Forge); behaviour fields incl. `heal_below` belong to the unit's AI profile, not the class; basic skills are NOT valid in a class path (visible only in the skills tab, available to every unit from level 1); the same accessory in both slots is forbidden via a FLAG (revisit stacking later); no limit on class path length (5 is only the ACTIVE class-skill slots): a standard level path where skills unlock at set levels, but schema and UI also support custom paths; the path is a dict {skill family: unlock level} chosen in the UI | User 2026-10-16 |
| FORGE1 round 4 answers (user 2026-10-16) | SKILL HIERARCHY: replace the `advanced` flag with a grade enum (novice, advanced, expert; expert is shown as an example of the hierarchy, no expert skill is implemented) and support a dependency structure: a skill may require several other skills (ALL required to learn it); every skill stays its own family, the hierarchy only gates which skills give access to learning another; if this proves too convoluted the link system is dropped for now and built later as a separate add-on system. Forge cannot create new basic skills. Promote-to-system IS undoable (system assets are used by tests and balance tuning, so the lock identifies tuning targets); deleting system assets goes through a SAFE DELETE process (reference scan over tests, seeds, classes, units; agent-driven) and users can clone or edit instead. Class gear loadout and class skill path are NOT locked on system classes (they are only defaults; units carry the real loadout and need not follow the class path). Standard unlock levels [1,3,4,5,7] and the missing-level-1-skill warning accepted. ONE HAND CATEGORY PER WEAPON FAMILY (either main or off, chosen where coverage is weaker): main-hand weapons are damage weapons, off-hand weapons are support weapons (shield, tome, orb); dagger, shortsword and knuckles become main-hand weapons; mixing is not allowed. The plain-1H-in-off-hand flag stays a code constant kept for legacy (dojo) support | User 2026-10-16 |
