## Goal

`arena_test_suite.gd` is about 1460 lines holding eight older test groups, and it is the main merge-conflict point. Split it into one file per group plus a registry, with NO behaviour or number changes, so future work adds new suite files without editing a shared file.

## Rules

1. Groups to extract (names may follow the existing headers): combat UI framework, character specs and inventory, gear equip UI and test dummy, combat session flow, art/terrain/zones, planning/stances/AP/AI. Each becomes `scripts/tests/<group>_test_suite.gd` with `class_name <Group>TestSuite` and a `static func run(tree_parent: Node = null) -> bool` (same signature shape as the existing suites).
2. A single registry (`SuiteRegistry`) lists every suite in run order and `ArenaTestSuite.run_all_tests` iterates it. New suites are added by one line in the registry only. Keep `ArenaTestSuite` as a thin runner (also keep the helper functions other suites call, e.g. `ArenaTestSuite._hand_ctx` and any shared statics: move them to a small shared helper file if needed and update callers).
3. Assertion output (PASS/FAIL text) must be identical so `check_project.ps1` and `fc.sh` counts do not change: total arena PASS before == after (currently 171) and dojo stays 42.
4. The older files that are also large (`combat_extensions_test_suite.gd` about 800 lines, `dojo_assertions.gd` about 770 lines) are OUT OF SCOPE here; only note in the report where natural split points are.
5. No edits outside `scripts/tests/` (plus `test_arena.gd` if required) and docs delta; no data changes.

## Acceptance checks

- `tools/fc.sh all` gives the identical PASS counts and zero FAIL; the order of suites in the log is unchanged (diff the list of `[Group]` lines before/after).
- `ArenaTestSuite` is under ~150 lines; no new suite file exceeds ~450 lines.
- Every previously public helper still resolves (grep the repo for `ArenaTestSuite.` callers).

## Out of scope

Behaviour changes, renaming tests, rewriting assertions, splitting other files.
